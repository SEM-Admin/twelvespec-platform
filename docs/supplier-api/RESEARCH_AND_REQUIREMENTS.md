# Metered supplier catalogs — research and implementation scope

Research date: 2026-11-09. Extension of the existing Supplier Integration Center, Catalog, Configuration, and customer RFQ modules. The original 20-module master inventory and its unpassed acceptance cases remain controlling; this work does not activate future modules or live purchasing.

## Findings and safe defaults

- [SAGE Connect](https://www.sageworld.com/connect/) currently advertises 5,000 monthly queries per Workplace license. Overage varies by query type. This is a public allowance description, not proof of this account's entitlement, remaining queries, service rates, redistribution rights, or provider-side spending limit. Historical 100-credit descriptions and other integrators' negotiated unlimited arrangements do not establish TwelveSpec's terms.
- [SAGE's official migration example](https://www.sagemember.com/kb/kb.dll/ViewArticle?ID=11679) documents HTTPS JSON POST to `https://www.promoplace.com/ws/ws.dll/ConnectAPI`, account ID/authentication key, category service101/version110 and product-search service103/version130. Current member documentation must confirm the selected read profile and response mapping. Workplace login credentials are not API credentials. Supplier write services are excluded.
- Exact current SAGE tariffs, accounting timezone, allowance consumption by other clients, caching/display license, and provider-side hard-stop behavior require confirmation under **SAGE Member → Developer APIs**. No paid SAGE request is authorized by this implementation task. Paid overage defaults to $0; unknown charges and unconfirmed current-period balances block requests. Public 5,000 is never automatically granted to a connection.
- [SinaLite official API documentation](https://api.sinaliteuppy.com/) names sandbox `https://api.sinaliteuppy.com` and live `https://liveapi.sinalite.com`; client-credentials exchange uses `/auth/token`, audience `https://apiconnect.sinalite.com`. Read catalog `/product`, general data `/product/{id}`, options `/product/{id}/{storeCode}`, and pricing-only POST `/price/{id}/{storeCode}` are distinct. Store9 is US/USD, store6 Canada/CAD. `/order/new` and all order writes are excluded.
- SinaLite's public sandbox list was verified previously:192 records,176 enabled. General data alone does not contain approved customer images, templates, configured quotes, or shipping. API signup email contains staging portal access, not a verified client ID/secret. API docs do not establish image rights or a per-call tariff; live activation therefore requires account terms confirmation. Sandbox observations are never promoted to live verification.

## Architecture and acceptance boundaries

A committed, shared-account ledger reserves every outbound request before dispatch, including authentication, failures and retries. Import transactions cannot roll back usage. Daily/monthly calls, minute burst, per-run call ceiling, operation units and monthly currency budget are configurable in Commerce OS. One account cannot obtain extra allowance by adding another connection. No automatic retry; timeouts retain conservative cost. Cache hits consume no external call; cache is private and entitlement-bound.

Credentials use authenticated encryption with a server environment key and scoped database ciphertext. Credentials/tokens are never included in public projections, logs, cached product responses or audit payloads. Runtime grants/RLS deny customer access to budgets, ledger, cache and ciphertext. Real metered access additionally requires an explicitly provisioned durable database; ephemeral preview state must fail closed. Financial approval is separate from storing a supplier account.

Imports preserve original source IDs and evidence, stage privately, and never auto-publish. Print option IDs remain distinct from apparel decoration choices; unknown MOQ, prices, availability, delivery, media and license terms remain unknown. Customer catalog views never make supplier API calls. Actual paid checkout, supplier ordering and unverified image/template ingestion remain disabled. Test runs use fixtures and SinaLite's public sandbox only until credentials, licensing, rates and budget approval are available.

## Account-specific documentation supplied by the owner (supersedes public summary)

The user's SAGE Member getting-started document (2026-11-09) establishes **per-user** authentication with `auth.acctId`, `auth.loginId`, and `auth.key`; its example uses service101/apiVer130. A licensed named user gets5,000 monthly credits; unused credits do not roll over or transfer. System/Public gets a **one-time**5,000-credit testing allowance, never replenished by a calendar rollover. Named-user credits must not serve anonymous website requests. These are separate login keys, not a cryptographic public/private pair.

Portal screenshots show service101 research lists and107 inventory as free;103 search,104 basic detail and105 full detail are fee-based after credits. Displayed remaining credits and query caps are observations, not ongoing balance guarantees. The System/Public paid-query limit is100 and the personal login shows unlimited; neither establishes a $0 provider hard stop. The owner's stated goal is no surprise charges, so no provider settings are changed and financial approval remains unset.

The same supplied guide permits caching with tenant-separated storage, continued active subscription and security responsibility; weekly refresh is a recommendation. The implementation limits cache TTL to one week and never shares SAGE data across customers or login allowances. Public customer browsing uses curated local catalog data, not per-page SAGE calls. Detailed module docs (request/response fields, unit fees and key-specific limits) still need verification before authenticated calls.
