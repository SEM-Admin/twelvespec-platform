Vermilion and accessibility

Using the WCAG relative-luminance formula, white text on #FF3F1A has contrast approximately 3.513:1. That is below the 4.5:1 minimum for ordinary text. Charcoal #17191B on that accent is approximately 5.018:1; white on charcoal is approximately 17.628:1. Preserve the requested accent while choosing appropriate label colors and large-text/decorative use. Do not round a borderline failing value into a pass. W3C contrast guidance.

The fresh mobile audit also found an accessible-name defect. Correct it alongside responsive control changes. The proposed theme cannot be accepted on desktop screenshots alone: test keyboard navigation, focus visibility, drawer behavior, 200% zoom, reduced motion and small-screen labels.

Publication and rollback

  1. Saving a draft checks the actor/resource permission, schema, references and expected row revision. It appends an immutable content revision. The public release remains unchanged.
  2. Preview renders that exact draft revision using the same component registry as the customer site. Desktop/tablet/mobile change only the viewport, not the underlying business data.
  3. Review assembles a release from the active manifest plus explicitly selected approved changes. It does not collect every unrelated draft in the workspace.
  4. Validation checks routes, required content, component versions, reference scope, publication/media rights, accessibility constraints and commercial action eligibility.
  5. One transaction writes the immutable release and changes the site's active release pointer. Audit/outbox records capture author, approver, reason and hashes. No deploy, Git commit or external email is part of routine content publication.
  6. Public reads use one release manifest for page/header/footer/theme consistency. Canonical products are still resolved through current published projections and availability gates.
  7. Page restore creates a draft from a selected old revision. Page rollback creates a new release from current content plus that page revision. Whole-site rollback is a separate owner action. Revalidate dependencies first; a revoked image or paused product must not be resurrected. Transactions and production documents are never rolled back by CMS actions.

Preview and caching

Prefer an authenticated same-origin OS preview using the shared renderer. Preview endpoints are read-only, require current permissions, return private/no-store responses and noindex metadata, and expose no commerce mutation controls. Do not use an unexpiring public shared-secret preview URL. If a storefront-tab preview is later needed, use a short-lived, scoped, revocable preview credential with fixed audience and validated internal destination. Do not share Better Auth cookies across origins or accept arbitrary redirects.

Next.js Draft Mode is a framework facility, not authorization by itself. Its preview isolation/cache behavior must be combined with the resource checks above. Draft Mode.

Cache published content by immutable release ID. Read the active release pointer consistently and invalidate publication/revocation paths explicitly. Next.js 16 revalidateTag(tag, 'max') permits stale content; it is not an immediate revocation guarantee. Use the current documented APIs and an explicit freshness policy, and test across the two app processes/any CDN rather than assuming one process's cache is global. Revalidation semantics.

Permissions and public data

  • Owner can independently edit, review and publish within the workspace after validation. Routine edits do not require a second employee or developer.
  • Marketing editors can edit assigned site documents and request review. Publishing, brand approval and navigation/global changes are separate capabilities.
  • A manager gets publication rights only through an explicit supported grant; repair the current module-role mismatch.
  • Store administrators edit only their granted organization sites; global brand/site edits require separate permission. Eligibility requires active membership on read, preview and asset paths.
  • Designers can prepare assets/templates without automatically receiving website-publication authority. Catalog managers retain catalog ownership.
  • Customers and anonymous visitors cannot read editorial drafts or studio APIs. Public pages receive an allowlisted published DTO; they do not receive raw content_assets, campaign audience records or staff metadata.
  • Do not treat the current anonymous demo-customer fallback as proof of organization membership. The published-only repository and its database reader/RLS policy must be proven in Phase 1 against the existing Better Auth/ts_runtime model.

Storage and scheduling dependencies

Use the already-approved isolated PostgreSQL environment and a provider-neutral asset-storage interface. The existing Supabase project is a candidate for durable development data/storage once verified TLS and access policies are resolved; no remote change was made during this audit. Keep originals/private client material in private storage, and deliver approved derivatives through scoped publication checks. Public buckets are not suitable for customer artwork. Storage access controls, bucket privacy.

Scheduled jobs need durable data and a reliable wake/execution mechanism. The current container can stop after inactivity, so a timestamp plus its local polling loop is insufficient. After review, choose and test an authorized development wake mechanism; any new infrastructure/cost requires the applicable approval. Do not enable a "scheduled" success state until that executor works. Late, stale or revoked jobs must fail visibly instead of publishing expired promotions silently.

Non-goals and safeguards

No second product database, second login, raw-HTML/CSS authoring surface, supplier scraper, PSRESTful, new paid service, production deployment or activation of unfinished features. Existing Coming Soon modules remain disabled. The technical schema below is a proposal, not a migration applied to a database.

The UUID strings above are explanatory placeholders; actual contracts validate UUIDs and references. Use discriminated schemas per block. Unknown properties, unknown blocks, unsupported versions, raw HTML, arbitrary CSS/scripts and unapproved remote media URLs are rejected. Rich text uses a bounded semantic AST with permitted marks/links. Reordering keeps section IDs stable.

The example JSON Schema describes a complete publication candidate. Phase 1 must also specify how incomplete but authorized drafts are persisted and shown with field errors, without allowing them to publish or accept unsafe references. Document shape validation never substitutes for database scope, rights, availability or permission checks.

row.revision is the optimistic concurrency version; content revision identity/version is the immutable history; schemaVersion describes document structure. These must not be conflated. Two editors saving the same base revision receive a conflict/diff workflow, not a silent last-writer-wins overwrite.

Navigation and brand documents

  • Navigation has stable group/item IDs, a maximum supported depth, semantic internal targets (page, collection, solution, store) or approved HTTPS external links, and optional approved featured-image IDs. Desktop mega menu and mobile navigation render the same document.
  • Page paths are unique within a site and checked against a reserved route registry: APIs, auth, products, designer, cart, account, bundles, stores and Coming Soon cannot be overwritten by editor slugs. Slug changes offer reviewed redirect entries in the release manifest.
  • Theme documents contain approved palette/font/style IDs, semantic token values, logo-variant references and inheritance rules. They do not accept raw CSS or replace an existing logo by default.
  • Organization overrides inherit the primary system's allowed structure. An organization editor cannot alter another store, global navigation, checkout rules, supplier data or financial settings.

Reference resolution and public projection

Editorial documents store stable IDs, not copied price/cost/variant objects. A product block resolves the canonical current published projection. If a referenced product is later paused or its derivative revoked, the public resolver removes/blocks that card safely; it does not resurrect the snapshot just because the page release is older. Quote lines retain their own immutable business snapshots and existing stale-revision checks.

Public page DTOs contain only approved text, resolved safe links, permitted theme values and approved derivative URLs/product projections. They exclude tenant-internal metadata, author emails, supplier names/credentials, wholesale costs, raw source payloads, campaign audiences, private asset keys and original artwork.

The published-only reader is a separate server-only repository contract. It must prove public-site visibility or current active organization membership before rendering page metadata, data or assets. An anonymous request must not inherit a seeded demo customer's private-store membership. The exact reader role/RLS implementation is an explicit Phase 1 security test.

Media contract

Metadata includes asset kind, original/derivative hash/version, owner/scope, dimensions/duration, alt text/caption, tags, focal point, rights status/scope/evidence reference/expiry and publication dependencies. Rights evidence remains private. Uploads are validated and quarantined; reusable public images are optimized, metadata-stripped derivatives. Product-specific catalog derivatives retain their exact product binding.

Private customer originals cannot be made public by inserting an asset ID into a hero or brand block. The picker filters permitted classes; the server and database validate the same rules. Approving a reusable marketing derivative is a deliberate action with a usage scope. Revocation and expiry block future reads/publication/rollback and trigger cache invalidation under a defined policy. No system can retract copies a visitor has already downloaded; do not claim instantaneous erasure of prior public downloads.

Campaigns, forms and downloadable material

  • Campaign pages reference campaign_id; changing content invalidates the relevant editorial approval without changing recipient consent or sending mail.
  • Project forms use the existing request/CRM domains. Submissions, attachments and personal data never become editable website-page JSON. Public inquiry support requires its own anti-abuse/privacy contract; existing authenticated RFQ remains the first supported handoff.
  • Design presets are approved reusable template documents/derivatives, not public copies of private customer projects. Manufacturing profiles remain Configuration/Creative/MIS records.
  • Downloadable PDFs/lookbooks reference approved derivatives generated from approved public content/product projections. Unsupported files, unscanned uploads and unimplemented export jobs remain unavailable until their tests pass.

Scheduling and lifecycle

Store scheduling instants in UTC plus the owner's selected display timezone. Resolve ambiguous/nonexistent daylight-saving times explicitly. Require an approved immutable release and expected current site generation; edit/cancel/revoke invalidates the queued job. Lock jobs and site activation transactionally, record idempotent effects, and surface late/expired jobs instead of silently publishing expired promotions.

Archive removes a document through a reviewed release, checking inbound navigation/references and redirects. Restore creates a new draft. Neither operation deletes audit history or reverses customer quotes, orders or payments. Durable backup/restore must recover the database, media and reference graph together.
